# Почему 1.0 и 2.0 показывали разное видео — 2026-11-10

> Обновление: по поручению пользователя способ перенесён в подписанную beta.12. Отдельная проверка выпускного APK и публикация описаны в [RELEASE_BETA12.md](RELEASE_BETA12.md). Ниже — история локального сравнения, а не текущий статус канала.

## Подтверждённые различия

1. В опубликованной beta.11 вход используется для каталога/подписок, а video access token запрашивается гостем. В 1.0.2 тот же пользовательский OAuth отправляется и при запросе видео. Это проверено по упакованному `assets/app/specific/Main.js` и read-only runtime старого приложения: `account_present=true`, `video_header_has_oauth=true`, `video_header_matches_account=true`.
2. В прежней локальной тестовой2.0 legacy-вход был подключён только к fullscreen. Catalog/sidebar previews оставались гостевыми. Значит, даже в тестовой сборке вход не распространялся на все live-пути.
3. Старое приложение передаёт `Play_PreviewURL` и `Play_PreviewResponseText` из предпросмотра в открываемый плеер. В2.0 выполнялся новый запрос видео. Это лишняя независимая video-сессия, способная получить другую выдачу Twitch. Самостоятельное влияние этого различия на частоту рекламы пока не измерено.
4. В старом клиенте есть исходники поддержки proxy, но в работающей проверенной копии **proxy выключен**. Это не объяснение полученного различия. Публичный APK1.0.2/code412 в старом проекте не изменялся.

У старого клиента также отличаются список запрашиваемых кодеков (`h265,h264`, у2.0 `avc1`), плеер и задержка эфира. В текущей проверке они не мешали обоим авторизованным клиентам показывать видео. Не объявляем их доказанной причиной заглушки. Точное правило рекламной выдачи Twitch и права аккаунта из этих наблюдений определить нельзя.

## Что исправлено в test.2

- Один `LiveSourceResolver` для preview карточки, sidebar preview и fullscreen. В экспериментальной сборке все три используют проверенную legacy-сессию, в штатной сборке сохраняется гостевой путь видео.
- Свежее получение источника при переходе preview→fullscreen заменено одноразовой передачей уже полученной ссылки. В памяти хранится только один кандидат до60с. При повторном открытии, другой identity/channel, истечении срока, ошибке авторизации или явном Retry источник получается заново.
- Запоздавший или отменённый preview не может заменить более новый результат. Ошибка аккаунта не вызывает скрытый гостевой fallback. Player и MediaSession по-прежнему принадлежат соответствующему UI, источник передаётся без разделения decoder между экранами.
- Signed URL/учётные данные не записываются на диск или в логи. Диагностика содержит только названия событий. Исправлен QA-helper: ошибка UiAutomator `null root node` больше не позволяет принять старый XML за текущий экран.

## Одновременное сравнение

Канал KaiCenat, одна машина/сеть. Старый клиент с аккаунтом на `Twitch20Release / emulator-5562` (API30), новый с аккаунтом на `Twitch20Modern / emulator-5564` (API36), тот же новый APK без аккаунта на `Twitch20Test / emulator-5560` (API30). Данные аккаунтов не переносились между приложениями, использованы ранее подтверждённые пользователем входы. Все открытия — реальные D-pad OK. ## Какие решения остаются разумными

Приоритет — единая авторизация видео и передача источника без лишнего открытия сессии, как в проверенном1.0. Эти различия устранены в test.2. Поддержка собственного Client ID для video endpoint ранее получила отказ Twitch, хотя официальный вход/Helix работает. Поэтому успех отдельного legacy-эксперимента не означает, что штатный Client ID внезапно стал подходить для видео.

Фильтрация рекламных сегментов не возвращает отсутствующее видео. Сам Streamlink описывает паузу вывода до возвращения контента и неизбежный разрыв: https://streamlink.github.io/cli/plugins/twitch.html#embedded-ads. Его описание ограничений сторонней авторизации также соответствует наблюдённому разделению account/video: https://streamlink.github.io/cli/plugins/twitch.html#authentication. Ненужный proxy или перебор playerType автоматически не добавлялись.

Границы: это наблюдение одного канала, текущего аккаунта и эмуляторов. Разные независимые сессии, API устройства и момент получения preview остаются переменными. Результат воспроизводит отличие гостя от аккаунта, но не доказывает отсутствие любых будущих midroll или работы на физическом TV. Использование legacy Client ID остаётся локальным экспериментом; Twitch требует отдельный идентификатор приложения: https://dev.twitch.tv/docs/authentication/register-app/.
